Developer-VM Image Rebuild - Status & Options

Prepared 2026-08-31 · Sources: VROOM-52268, RHELDST-44190, Slack #thread, Juanje Ojeda investigation doc

The problem

RHIVOS 2.0 introduces two customer-facing Developer VM (installer) qcow2 images - RHIVOS-2.0-Core and RHIVOS-2.0 (FuSa), each x86_64 + aarch64 - used to install RHIVOS from a non-RHIVOS VM. Today they are built by RHIVOS's own pipeline (automotive-image-builder / osbuild) and stored on AWS S3.

ProdSec blocks distribution of images built outside approved tools. The approval chain (per Kanitha Chim):

  • S3 → CDN → customer portal = NOT approved (built outside brew/konflux)
  • Brew | Konflux → CDN → customer portal = approved (prodsec-approved build tool)

Key insight: the customer-portal download page is just a UI over the CDN. Once an image is on CDN, RHIVOS only informs the teamnado team to mirror it - there is no separate upload hop. All RHEL images on the download pages ship via CDN.

Why there is no exception path
  • As of May 26, 2026, Chris Wright eliminated all exceptions to RH-SDLC, company-wide. Only images built via approved systems (Brew/Konflux) and delivered through authorized channels (CDN / Unified Downloader) can reach customers. A VP exception now needs VP sign-off and is reserved for rare cases - not a realistic route here.
  • The Developer VM environment falls under the EU Cyber Resilience Act (CRA), mandatory for the EU market. An integrated approved toolchain is the cleanest CRA + RH-SDLC fit.
  • Scope is only these images, not the full RHIVOS image set. GA is potentially September 2026 (not confirmed) - no locked date, but it must be resolved regardless.

The two viable options

Both are ProdSec-approved. The difference is CDN publication and onboarding cost.

Option A - Konflux Preferred

Build everything in Konflux, end to end:

Phase 1: build bootc container from RHIVOS compose repos | (auto via build-nudges-ref) v Phase 2: bootc -> QCOW2 (build-vm-image, priv VM) | (auto via Integration Service) v Phase 3: publish to CDN (push-disk-images-to-cdn)

Why preferred: single approved toolchain from build through distribution; CDN publication is integrated (automatic via ReleasePlanAdmission); RHEL AI already does exactly this (bootc → qcow2 → CDN), proven and documented; no intermediate storage or manual staging; cleanest for EU CRA + RH-SDLC; lowest long-term maintenance.

What is needed: Containerfile installing from RHIVOS compose repos + redhat-release-automotive(-core); BIB config YAML; ~12 config artifacts in konflux-release-data (Application, Components, ReleasePlan, RPA, ECP), all templated from RHEL AI; Pulp CDN label + Content Gateway codes; tenant onboarding. Uses build-vm-image v0.3 + push-disk-images-to-cdn. No new pipeline code.

Option B - Brew / Image Builder

Build the qcow via Image Builder in Brew, then manually stage and push to CDN.

brew osbuild-image <name> <ver> <distro> <target> <arch> --image-type qcow2 --repo <compose-url> | v Manual staging pub push-staged -> cdn-stage / cdn-live

Pros: Joe Amato recommends it as the lowest barrier for a tight timeline; SOA-certified (ProdSec Security Operating Approval); Pungi integration possible (auto builds per compose).

Cons: Image Builder team must define a RHIVOS "distro" (potential bottleneck); CDN publication is a separate manual step; needs a Brew target + whitelisted package name; RHIVOS has never had images in Brew; two disconnected systems to maintain vs one integrated flow.

Potential blockers

  • Tenant onboarding (Konflux): a new RHIVOS tenant needs RelEng approval - unknown lead time; this is the key open question.
  • Pulp destination / CGW codes (both paths): Content Delivery must create the Pulp CDN repository label and Content Gateway product entry.
  • BIB deprecation (long-term): bootc-image-builder was archived upstream June 2026. Still supported in the RHEL 10 lifecycle; the replacement is the image-builder CLI. Not a blocker now, but it touches the Konflux build-vm-image path (which wraps BIB).

No hard technical blockers - both paths are feasible with existing tooling.

Recommendation and decision point

Recommendation The investigation doc weakens Option B's main selling point. The "Brew for the timeline" argument rested on an early-September GA - but no date is locked. Remove the deadline pressure and Konflux wins on every axis except tenant-onboarding lead time: one approved toolchain, integrated CDN, CRA/SDLC-clean, RHEL-AI-proven, ~12 templated YAMLs.

The decision effectively collapses to one question: what is the Konflux tenant-onboarding lead time? If it is tolerable, Konflux is the clear choice. That is exactly Juanje's next step - ask RelEng.

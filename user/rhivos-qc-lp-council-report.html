Executive Summary

Three independent perspectives analyzed the RHIVOS Qualcomm Layered Product initiative from scratch, reviewing Petr Sabata's AUTOBU-1076 ticket, the RHEL-for-NVIDIA (Voyager) architecture, the ATC build and pipeline codebase, the AIB wiki, and the May 20 Release Readiness meeting findings.

The September LP availability date is at risk — not because the engineering is hard, but because the external team dependencies (RHELDST, RHELWF, ENGCMP, RCM) have not been formally engaged. These teams have multi-week lead times, and the dependency chain has three blocking layers that must resolve in sequence. Work that should already be in flight is not yet started.

The prior analysis was largely sound but incomplete. Seven technical gaps were identified that were not previously surfaced: missing compose promotion pipeline, undefined ET configuration, undecomposed gating (resultsdb/waiverdb/greenwave), Test Console dual-product gap, S3 access control, dist-git workflow for QC packages, and pesign build targets for the QC kernel. The SKU/Eng Product decision is structurally forced — the "extensions repo" alternative (Voyager Option b) cannot satisfy the Qualcomm access control requirement and should be formally closed.

Validate or Challenge — Prior Conclusions

✓ Confirmed

Two-compose design is not a preference — it's technically forced. Voyager's docs confirm Pungi cannot handle two builds of the same package name in different compose variants. If QC ships a kernel (kernel-ivos-qualcomm already exists in the pipeline), the two-compose design is mandatory, not optional.

✓ Confirmed

Dist-tag isolation is required. Voyager uses .el10nv to distinguish RPMs from RHEL equivalents. RHIVOS QC LP needs .el10qc or .el10ivos so QC RPMs are distinguishable at the repo and advisory level.

⚠ Oversimplified

Build system: pesign targets missing. The kernel must go through a two-phase build (standard target → pesign target). The Brew tag structure must include pesign-capable targets from day one. The prior analysis did not mention this.

⚠ Oversimplified

AIB: not zero manifest changes. Adding a QC LP repo requires a new @ADD_QCOM_LP_REPO_*@ placeholder token, new/modified .sed files per QC target, and updates to create-qa-manifest.sh. It's manifest code change, not zero change.

✓ Strengthened

Separate Eng Product is structurally determined. Voyager's Decision #8 rejected a new Eng Product because no access control was needed. For RHIVOS QC LP, access control IS the central requirement. Voyager Option (b) is not available. This is confirmed, not tentative.

Technical Gaps — What Was Not Previously Identified

  • G1
    ODCS compose registration not owned

    Adding a QC LP compose requires an ODCS playbook MR filed with ENGCMP (CTS system). Who writes the QC LP Pungi config, where it lives (new branch in rhivos.git? new repo?), and who registers it with ODCS — completely undefined.

  • G2
    Compose promotion pipeline is entirely missing

    Voyager's Minimal compose feeds ET product listings via an automated promotion chain (CTS tag → UMB message → Jenkins job → ET ComposeDB import). RHIVOS's promote-compose uses SSH/Kerberos to an RCM host — a different mechanism. Without an equivalent for the QC LP Minimal compose, ET advisories will be stuck in NEW_FILES state (exactly Voyager's ENGCMP-6387 problem). RHELCMP engagement required.

  • G3
    ET configuration entirely unspecified

    Voyager defined: separate ET Product, one Product Version (RHEL-10-Nvidia), one Variant (10Base-RHEL-Nvidia), $releasever-free CDN path. For QC LP: none of this exists. ET Product name? Variant names? RHIVOS versioning or Voyager-style? Who creates it (RHELWF/OSCI)? Blocking for advisory automation.

  • G4
    Gating stack (resultsdb / waiverdb / greenwave / Gator) not decomposed

    The current GATOR_CONF is for RHIVOS base packages. QC LP needs: a separate Gator config path; resultsdb associations for QC NVRs; waiverdb waiver subjects; greenwave policies for QC Brew tag content. Petr's ticket flags all of this — but none of it is designed.

  • G5
    Test Console dual-compose submission not designed

    tc_wait_for_rhivos_test() in functions.yml uses tc-cli rhivos base-image is-complete — rhivos is a hardcoded product identifier. QC platform images built from dual-compose (RHIVOS + QC LP) need TC to accept and track a combined submission. May require new TC pipeline request types or API changes — not a config tweak.

  • G6
    S3 artifact access control for proprietary QC bits undefined

    QC LP artifacts contain proprietary Qualcomm content before the CDN push. The existing auto-product-build-downstream bucket may not have the right IAM policies. New bucket vs. policy extension is flagged in the ticket — still unaddressed.

  • G7
    No dist-git workflow for QC package maintainers

    RHIVOS currently composes from a Koji tag directly — no traditional dist-git/RoG workflow. QC package maintainers need a defined submission path (dist-git branch naming, Brew build target, RoG or rhpkg build equivalent). Without this, "user space packaging complete by August" does not mean builds are in the right Brew tag for the compose.

Engineering Risks

  • R1
    Compose promotion pipeline not RHIVOS-owned

    promote-compose does SSH to RCM host. Voyager's ET listing import is a separate Jenkins job (RHELCMP-15186) owned by RHELCMP. If RHIVOS assumes it can reuse its job, the ET product listing import step will be missed and advisories will fail. RHELCMP engagement is required, not optional.

  • R2
    August/September timeline vs. Layer 2 lead times

    RHELBLD, RHELWF, and RHELDST infrastructure setup items have 4–6 week lead times based on Voyager precedent (RHELBLD-17745 through -18191 spanned months). Starting Layer 2 engagement now is necessary — waiting until August packaging completes will miss September.

  • R3
    QC LP compose entitlement gating may break the AIB pipeline

    If the QC LP compose URL requires partner credentials, the existing Kerberos keytab (KEYTAB_ODCS) won't satisfy it. The AIB build stage receives compose URLs directly. Needs explicit RHELDST confirmation that the internal (pre-CDN-push) compose URL is accessible without per-user entitlement.

  • R4
    @PLACEHOLDER@ substitution gaps in manifests are silently destructive

    Any QC LP repo token left unreplaced in a default.sed fallback (used by ps.aib.yml.in and fusa-minimal.aib.yml.in) emits a broken manifest that only surfaces as a boot failure on hardware, not a build error.

  • R5
    No dist-git workflow for QC package maintainers

    RHIVOS composes from a Koji tag directly — no traditional dist-git/RoG. QC vendors need a defined submission path before they start packaging. "User space packaging complete end of August" requires this workflow to exist and be communicated well before August.

Full LP vs. Extensions Repo — What's Actually Different?

Extensions repo approach (Voyager Option b) — NOT available

Whitney's instinct toward the simpler "extensions repo" path references how Voyager (RHEL-for-NVIDIA) avoided overhead: no separate SKU, no separate Eng ID, available to all RHEL subscribers. That worked because NVIDIA hardware is open — no access gating needed. For RHIVOS QC LP, Qualcomm partner agreements require gated access. The extensions repo approach has no access control mechanism and cannot satisfy this requirement. The choice is structurally forced, not a preference call.

What the Voyager model DOES contribute

CDN layered path structure (/content/dist/layered/...), disabled-by-default repo, two-compose design (Minimal for CDN alignment + ET, Complete for image builds) — all applicable regardless of SKU decision. Juanje's "build internally, separate at CDN" proposal aligns with this. The build and distribution mechanism is reusable; the access model is not.

Product Recommendations with Tradeoffs

Rec 1 — Confirm separate SKU as unavoidable; stop treating it as optional

The overhead concern is valid but continuing to hold "extensions repo" as a live alternative delays architecture decisions. Close it out with the SP release team consultation (Whitney's action item) and communicate clearly so teams can proceed.
Tradeoff: Higher org overhead, but no alternative satisfies the contractual requirement.

Rec 2 — Scope September LP to user space only; kernel is a follow-on

Don't let kernel legal uncertainty delay user space LP. Treat them as sequential components of the same LP. Communicate this explicitly to Qualcomm and customers upfront.
Tradeoff: Customers get audio/camera/graphics/display first, kernel later — acceptable if stated clearly.

Rec 3 — Align pipeline access model before August packaging completes

The QC LP compose URL access question needs an answer from RHELDST before the September date. Not a last-minute task — credential handling design, testing, and operation takes weeks.
Tradeoff: Forces RHELDST conversation earlier than comfortable, but late is unrecoverable.

Rec 4 — Define product name and customer concept now

Portal, documentation, entitlement flow, and support all depend on stable product identity. Deferring to launch creates rework across multiple teams.
Tradeoff: Early naming may need revision, but late naming is more expensive.

Rec 5 — Explicitly resolve RHIVOS vs. RHIVOS Core LP scope

If both variants get the QC LP, design that now — adding it later doubles entitlement and ET setup work. If only one gets it, say so and communicate to partners.
Tradeoff: Early commitment constrains flexibility but prevents late-stage scope collapse.

Cross-Cutting Synthesis — Where All Three Perspectives Agree

Three independent perspectives converge on five themes:

  • The September date is at risk from external dependencies, not engineering. The work ATC controls (packaging, pipeline, manifests) is feasible. The blockers are RHELDST, RHELWF, ENGCMP, RHELCMP, and the portal team — none of which have been formally engaged with scope and deliverables.
  • The separate SKU/Eng Product decision is structurally determined and should be closed immediately. Continuing to hold the "extensions repo" alternative open delays architecture decisions across all teams without any upside — the access control requirement makes the outcome clear.
  • The Voyager distribution model is directly applicable; the Voyager build toolchain is not. CDN layered path, disabled-by-default repo, two-compose design (Minimal + Complete) — all reusable. Image-during-compose, Pungi/ODCS toolchain specifics, independent versioning — none of this applies. The meeting's "Voyager doesn't fit" conclusion was too broad; it's the build layer that doesn't fit, not the distribution model.
  • Seven technical gaps were not identified in the prior analysis — the most critical being the missing compose promotion pipeline (required for ET product listings), the undefined gating stack configuration, and the absence of a dist-git workflow for QC package maintainers.
  • The QC kernel legal decision must not be allowed to hold the user space LP hostage. Scope-lock September to user space only in writing. Design the architecture to accommodate kernel as an additive scope item, not a redesign trigger.

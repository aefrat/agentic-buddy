Executive Summary

Three independent perspectives analyzed the RHIVOS Qualcomm Layered Product initiative from scratch, reviewing Petr Sabata's AUTOBU-1076 ticket, the RHEL-for-NVIDIA (Voyager) architecture, the ATC build and pipeline codebase, the AIB wiki, and the May 20 Release Readiness meeting findings.

A key finding from reviewing the custom-images AIB manifest repository: Qualcomm packages (including kernel-ivos-qualcomm) do not currently come from Brew or the RHIVOS compose — they come from Qualcomm COPR repos, injected into AIB manifests via per-target .sed substitution. There is no Brew tag, no gating, and no ET advisories for this content today. The QC LP initiative is therefore replacing COPR with a formal distribution channel, not adding a compose alongside an existing one. This makes the SKU/access control requirement concrete: COPR is public today; the LP is the first point QC content is formally gated.

The September LP availability date is at risk — not because the engineering is hard, but because the external team dependencies (RHELDST, RHELWF, ENGCMP, RCM) have not been formally engaged. These teams have multi-week lead times, and the dependency chain has three blocking layers that must resolve in sequence. Work that should already be in flight is not yet started.

The prior analysis was largely sound but incomplete. Seven technical gaps were identified that were not previously surfaced: missing compose promotion pipeline, undefined ET configuration, undecomposed gating (resultsdb/waiverdb/greenwave), Test Console dual-product gap, S3 access control, dist-git workflow for QC packages, and pesign build targets for the QC kernel. The SKU/Eng Product decision is structurally forced — both lower-overhead alternatives evaluated by the Voyager team are inapplicable to RHIVOS. "Extensions" in Petr's ticket refers to a specific named RHEL content-set (alongside BaseOS and AppStream) — Voyager's Option (a), rejected because it requires unique package names and ties to the RHEL schedule. Voyager's chosen Option (b) — a new repo under the existing RHEL Eng Product — also cannot work for RHIVOS: it has no access control mechanism and is available to all RHEL subscribers. Only Option (c), a new Eng Product with a separate SKU, satisfies the Qualcomm partner access requirement. This should be formally confirmed and closed.

Validate or Challenge — Prior Conclusions

⚠ Revised — constraint does not apply to RHIVOS QC LP

Two-compose was technically forced for Voyager — but not for the same reason RHIVOS needs it. Voyager's two-compose design was forced by a package name collision: NVIDIA ships a kernel with the same name as RHEL's standard kernel, and Pungi cannot handle two builds of the same package name in different variants of one compose. RHIVOS does not have this problem. The Qualcomm kernel is kernel-ivos-qualcomm — a distinct name from kernel-automotive. QC LP packages are additive (unique names, no RHIVOS base package is being replaced), so Pungi sees no naming conflict.

A separate Minimal compose for QC LP is still needed — for CDN alignment (the disabled-by-default LP repo path) and for Errata Tool product listing import. But the reason is architectural (CDN/ET requirements), not a Pungi workaround. This distinction matters for scoping: RHIVOS could in principle build QC LP images from a single compose; the split is driven by distribution requirements, not build tooling constraints.

✓ Confirmed

Dist-tag isolation is required. Voyager uses .el10nv to distinguish RPMs from RHEL equivalents. RHIVOS QC LP needs .el10qc or .el10ivos so QC RPMs are distinguishable at the repo and advisory level.

⚠ Oversimplified

Build system: pesign targets missing. The kernel must go through a two-phase build (standard target → pesign target). The Brew tag structure must include pesign-capable targets from day one. The prior analysis did not mention this.

⚠ Oversimplified

AIB: not zero manifest changes. Adding a QC LP repo requires a new @ADD_QCOM_LP_REPO_*@ placeholder token, new/modified .sed files per QC target, and updates to create-qa-manifest.sh. It's manifest code change, not zero change.

✓ New finding — QC packages today come from COPR, not Brew

The LP work is replacing COPR with a formal distribution channel — not adding a compose alongside an existing one. Review of the custom-images AIB manifest repo confirms that kernel-ivos-qualcomm and other QC packages are currently fetched from Qualcomm COPR repos at image build time, injected via @ADD_QCOM_BOARD_SUPPORT_*@ placeholder substitution in per-target .sed files. There is no Brew tag, no ODCS compose, no Gator gating, and no ET advisories for this content today.

The LP changes this end-to-end: kernel-ivos-qualcomm built in Brew → rhivos-qc-2.1-candidate tag → QC LP ODCS compose → CDN behind QC SKU → @ADD_QCOM_LP_REPO_*@ sed substitution (new placeholder, same pattern) → AIB image build. The @ADD_QCOM_BOARD_SUPPORT_*@ pattern is the exact hook point. COPR is effectively public today; the LP is the first point at which QC content is formally gated. This makes the access control requirement concrete, not theoretical.

⚠ Corrected — Source doc has wrong AIB assumption

Petr's brainstorming doc states: "AIB might need to be extended to support multiple product subscriptions, although this might work transparently via librhsm." This is incorrect. AIB does not use subscription-manager or librhsm in the build path at all — it uses explicit content.repos baseurl lists in YAML manifests. The question is not about subscription support; it's about whether the QC LP compose URL is entitlement-gated (requiring pipeline credential handling) and about adding new @PLACEHOLDER@ tokens to the manifest templates. Contact: Alexander Larsson (named in Petr's doc).

✓ Strengthened

Separate Eng Product is structurally determined. The Voyager team evaluated four delivery options. Option (a) — push into the existing Extensions content-set — was rejected because it requires unique package names and ties to the RHEL schedule. Option (b) — new repo under the existing RHEL Eng Product — is what Voyager chose, but only because all RHEL subscribers can access NVIDIA content; no access control is needed. For RHIVOS QC LP, access control is the central requirement: neither Option (a) nor Option (b) provides per-partner gating. Only Option (c) — new Eng Product with a separate SKU — satisfies it. This is confirmed, not tentative.

Technical Gaps — What Was Not Previously Identified

  • G1
    ODCS compose registration not owned

    Adding a QC LP compose requires an ODCS playbook MR filed with ENGCMP (CTS system). Who writes the QC LP Pungi config, where it lives (new branch in rhivos.git? new repo?), and who registers it with ODCS — completely undefined.

  • G2
    Compose promotion pipeline is entirely missing

    Voyager's Minimal compose feeds ET product listings via an automated promotion chain (CTS tag → UMB message → Jenkins job → ET ComposeDB import). RHIVOS's promote-compose uses SSH/Kerberos to an RCM host — a different mechanism. Without an equivalent for the QC LP Minimal compose, ET advisories will be stuck in NEW_FILES state (exactly Voyager's ENGCMP-6387 problem). RHELCMP engagement required.

  • G3
    ET configuration entirely unspecified

    Voyager defined: separate ET Product, one Product Version (RHEL-10-Nvidia), one Variant (10Base-RHEL-Nvidia), $releasever-free CDN path. For QC LP: none of this exists. ET Product name? Variant names? RHIVOS versioning or Voyager-style? Who creates it (RHELWF/OSCI)? Blocking for advisory automation.

  • G4
    Gating stack (resultsdb / waiverdb / greenwave / Gator) not decomposed

    The current GATOR_CONF is for RHIVOS base packages. QC LP needs: a separate Gator config path; resultsdb associations for QC NVRs; waiverdb waiver subjects; greenwave policies for QC Brew tag content. Petr's ticket flags all of this — but none of it is designed.

  • G5
    Test Console dual-compose submission not designed

    tc_wait_for_rhivos_test() in functions.yml uses tc-cli rhivos base-image is-complete — rhivos is a hardcoded product identifier. QC platform images built from dual-compose (RHIVOS + QC LP) need TC to accept and track a combined submission. May require new TC pipeline request types or API changes — not a config tweak.

  • G6
    S3 artifact access control for proprietary QC bits undefined

    QC LP artifacts contain proprietary Qualcomm content before the CDN push. The existing auto-product-build-downstream bucket may not have the right IAM policies. New bucket vs. policy extension is flagged in the ticket — still unaddressed.

  • G7
    No dist-git workflow for QC package maintainers

    RHIVOS currently composes from a Koji tag directly — no traditional dist-git/RoG workflow. QC package maintainers need a defined submission path (dist-git branch naming, Brew build target, RoG or rhpkg build equivalent). Without this, "user space packaging complete by August" does not mean builds are in the right Brew tag for the compose.

  • G8
    Product security configuration entirely absent — CPE strings, SWID tags, PSIRT

    Not mentioned in the prior analysis at all. Petr's brainstorming doc identifies three distinct items: (1) CPE strings must be defined and configured in Errata Tool for the QC LP product — without this, CVE tracking against QC LP packages is impossible; (2) SWID tag delivery mechanism must be investigated — do they ship in an RPM? separate path?; (3) PSIRT configuration for the separate QC LP tags and composes must be set up. Contact: Charles Timko. This work belongs to Layer 2 but has not been scoped or assigned.

  • G9
    Customer documentation entirely unassigned

    Petr's doc names Dana Walker (?) as a potential contact but marks it as unconfirmed. No documentation owner, no scope, no draft. Customers need guidance on: how to access QC LP content, how to enable the LP repo, and how to build images from RHIVOS + QC LP in the AIB context (pipeline manifest changes, content.repos). This is not a late-stage concern — access instructions must exist before LP goes live. Contact: Dana Walker (unconfirmed).

Engineering Risks

  • R1
    Compose promotion pipeline not RHIVOS-owned

    promote-compose does SSH to RCM host. Voyager's ET listing import is a separate Jenkins job (RHELCMP-15186) owned by RHELCMP. If RHIVOS assumes it can reuse its job, the ET product listing import step will be missed and advisories will fail. RHELCMP engagement is required, not optional.

  • R2
    August/September timeline vs. Layer 2 lead times

    RHELBLD, RHELWF, and RHELDST infrastructure setup items have 4–6 week lead times based on Voyager precedent (RHELBLD-17745 through -18191 spanned months). Starting Layer 2 engagement now is necessary — waiting until August packaging completes will miss September.

  • R3
    QC LP compose entitlement gating may break the AIB pipeline

    If the QC LP compose URL requires partner credentials, the existing Kerberos keytab (KEYTAB_ODCS) won't satisfy it. The AIB build stage receives compose URLs directly. Needs explicit RHELDST confirmation that the internal (pre-CDN-push) compose URL is accessible without per-user entitlement.

  • R4
    @PLACEHOLDER@ substitution gaps in manifests are silently destructive

    Any QC LP repo token left unreplaced in a default.sed fallback (used by ps.aib.yml.in and fusa-minimal.aib.yml.in) emits a broken manifest that only surfaces as a boot failure on hardware, not a build error.

  • R5
    No dist-git workflow for QC package maintainers

    RHIVOS composes from a Koji tag directly — no traditional dist-git/RoG. QC vendors need a defined submission path before they start packaging. "User space packaging complete end of August" requires this workflow to exist and be communicated well before August.

Pipeline & Gating — Specific Changes Required
Addressing Juanje's "only distribution changes needed" framing from the RHIVOS Release Readiness Meeting of May 20

Is Juanje's statement still correct?

What's correct

The core build infrastructure is unchanged — packages still go through the same Brew/Koji process, the same ODCS compose mechanism, the same AIB image build flow. The heaviest work is at the distribution layer (new Eng Product, SKU, CDN layered path, Errata Tool). The build architecture doesn't need redesign.

What's undersold

"No pipeline changes" is not accurate. The council analysis identified ~5 new pipeline components that must be built. These are additions, not redesigns — but they require scoping, ownership, and non-trivial implementation effort. Zero estimates exist today.

Pipeline Changes — downstream-pipelines-as-code

  • 1
    New release config in release-configs/

    A new BUILD_BRANCH entry (e.g., latest-RHIVOS-2-QC) with QC LP compose URLs, a separate GATOR_CONF path, and component pins. Same pattern as existing stream configs — but must be written, tested via MR, and operational before the LP is available.

  • 2
    Dual-compose injection into the generate-compose / build stage

    The pipeline currently runs one ODCS request → one compose URL → AIB build. For QC LP images, both the RHIVOS base compose URL and the QC LP compose URL must be available to the AIB build stage. Either a second ODCS call is added, or the QC LP compose URL is injected via a release config variable.

  • 3
    S3 artifact access control for QC LP builds

    QC LP artifacts contain proprietary Qualcomm content before the CDN push. Decision needed: new S3 bucket vs. scoped IAM policy on existing auto-product-build-downstream. Pipeline runner permissions must be extended to cover the new path. Petr's ticket flags this explicitly.

  • 4
    Compose promotion pipeline for QC LP Minimal compose

    The step that imports product listings into Errata Tool (making ET advisories functional) requires an automated promotion chain: CTS tag → ET ComposeDB import. The existing RHIVOS promote-compose job does SSH/Kerberos to the RCM host — a different mechanism than Voyager's Jenkins job (RHELCMP-15186). Without this, QC LP advisories will be stuck in NEW_FILES. RHELCMP engagement required. This pipeline does not exist and is not trivial.

AIB Manifest Changes — custom-images

  • 5
    New @ADD_QCOM_LP_REPO_*@ placeholder tokens in templates

    Add to qa.aib.yml.in and ps.aib.yml.in, following the existing @ADD_QCOM_BOARD_SUPPORT_*@ pattern. Every .sed file in the corresponding options directory must provide a substitution — or the raw token appears in the manifest and causes a silent broken build.

  • 6
    New .sed entries per QC hardware target

    Add QC LP repo URL substitutions to ride4_sa8775p_sx_r3.sed, ride4_sa8650p_sx_r3.sed, and related Qualcomm target files. Non-QC targets need a no-op substitution in their default.sed. Caution: create-qa-manifest.sh uses --require, so missing a QC target sed fails hard; ps and fusa-minimal use default.sed fallback, so a missed substitution there emits a broken manifest silently.

  • 7
    Updates to create-qa-manifest.sh

    Logic to apply the QC LP sed block conditionally — when building for a RHIVOS + QC distro/target combination. Pattern already exists for the CA cert injection ([[ "$DISTRO" =~ rhivos ]]) — same approach applies here.

Gating Changes — Gator / resultsdb / waiverdb / greenwave

  • 8
    Separate GATOR_CONF for QC LP in automotive/fences/gating/gator

    The current Gator config covers RHIVOS base packages. QC LP needs its own config path with: (a) Test Console test triggers for QC packages, and (b) evaluation/contact-point triggers on gate failure (Petr's ticket explicitly lists both). This is a new Gator config file, not an extension of the existing one.

  • 9
    resultsdb — new subject associations for QC LP NVRs

    Test results must be submittable and queryable against QC LP package builds, which have distinct NVRs from QC Brew tags. resultsdb must know to associate these with the QC LP product, not the base RHIVOS product.

  • 10
    waiverdb — waiver subjects scoped to QC LP tag

    Waivers for QC LP packages must be expressible without affecting RHIVOS base package gating. QC LP Brew tag content needs its own waiver subject namespace.

  • 11
    greenwave — new policies for QC LP Brew tag

    A greenwave policy defines what constitutes a passing gate. RHIVOS base policy must not automatically apply to QC LP packages — they may have different gating criteria (e.g., fewer required test plans for user space vs. kernel). New policy required.

Test Console — Dual-Compose Smoke Tests

  • 12
    TC product identifier for QC platform images

    tc_wait_for_rhivos_test() in functions.yml calls tc-cli rhivos base-image is-complete — rhivos is hardcoded as the product type. QC platform images built from dual-compose (RHIVOS + QC LP) may need a new TC pipeline request type or a configurable product identifier. Petr's ticket flags this: "TC hardcoding for RHIVOS needs removal." Needs explicit TC team confirmation — may not be a config change.

  • 13
    New smoke test jobs in extends.yml for QC platform dual-compose images

    Once TC supports dual-compose submission, the existing Qualcomm hardware smoke test jobs (smoke-tests-ride4-sa8775p-sx, smoke-tests-ride4-sa8650p-sx-r3) need to be extended or new jobs added that run against images built with both the RHIVOS base compose and the QC LP compose.

Full LP vs. Extensions Repo — What's Actually Different?

What "Extensions" actually means — technical definition

"Extensions" is a specific named RHEL content-set — a concrete repo alongside BaseOS and AppStream in RHEL's standard repo structure (e.g., rhel-10-for-aarch64-extensions-rpms). It is not a generic term for adding content somewhere. Petr's ticket and Whitney's meeting comment both reference this because the Voyager team formally evaluated it as delivery Option (a) and rejected it. Option (b) — what Voyager actually chose — is a different option: a new repo under the existing RHEL Eng Product. Both Options (a) and (b) are inapplicable to RHIVOS QC LP, for different reasons.

Option (a) — Push into the Extensions repo — Rejected by Voyager, also fails for RHIVOS

Push LP packages directly into the existing RHEL Extensions content-set. No new repos, no new Eng Product, no new SKUs — the theoretically lowest-overhead path.

Why Voyager rejected it: (1) Requires unique package names (e.g., kernel-nv) to avoid conflicts with RHEL base packages sharing the same repo. (2) Ties the LP to RHEL's release schedule — no independent cadence possible.

Why it also fails for RHIVOS: No access control mechanism exists at this level. Extensions packages are available to all RHEL subscribers — cannot satisfy Qualcomm partner agreements.

Option (b) — New repo under existing RHEL Eng Product — Voyager's choice, also fails for RHIVOS

A new dedicated repo (e.g., /content/dist/layered/rhel10/aarch64/nvidia/os) alongside BaseOS/AppStream/Extensions, under the same existing RHEL Eng Product. Disabled by default; enabled with a content-set entitlement. No separate SKU, no separate Eng Product.

Why Voyager chose it: No access control was needed (NVIDIA hardware is open to all RHEL subscribers). Independent CDN path, no package naming constraints, independent cadence — all met with minimal overhead.

Why it fails for RHIVOS: Available to all RHEL subscribers. There is no per-partner entitlement gating below the Eng Product level. Qualcomm gated access cannot be implemented within Option (b).

When Whitney references "the extensions repo approach" or "the lower overhead path," she is describing Option (b) — not literally the Extensions content-set. The label is imprecise but the concern is real. Option (b) is still not available to RHIVOS.

What the Voyager model DOES contribute — distribution layer only

CDN layered path structure (/content/dist/layered/...), disabled-by-default repo, two-compose design (Minimal for CDN alignment + ET, Complete for image builds) — all applicable regardless of SKU decision. Juanje's "build internally, separate at CDN" proposal aligns with this. The distribution mechanism is reusable; the access model is not.

Conclusion — Option (c) is structurally determined, not a preference call

Only Option (c) — new Eng Product with a separate SKU — can satisfy the Qualcomm access control requirement. This follows directly from the partner agreement requirement, not from engineering preference. Whitney's overhead concern is valid but irreducible. The right action is to confirm and close this decision with the release SP team (Whitney's action item), then engage the portal team with a concrete scope. Continuing to hold Option (b) as a live alternative delays architecture decisions across all downstream teams.

Reviewed the RHEL-for-NVIDIA (Voyager) knowledge base at https://gitlab.cee.redhat.com/tmlcoch/rhel-for-nvidia-knowledge against this ticket's requirements.

✅ What maps well from Voyager (~5 of 8 areas)

  • Build system: Voyager's versioned Brew tag structure (nv-{ver}-rhel-10 with candidate/pending/build/et-compose hierarchy) is a direct reference for our LP tag design.
  • Distribution layer (CDN + ET) patterns: Voyager's CDN layered path (/content/dist/layered/...), disabled-by-default repo, and separate ET Product + Variant for the LP advisory stream are the right reference. Voyager's two-compose design (Minimal + Complete) is not applicable: it was forced by a Pungi package-name collision (NVIDIA ships a kernel named kernel, same as RHEL's). RHIVOS has no such conflict — kernel-ivos-qualcomm ≠ kernel-automotive. Per Juanje's clarification (confirmed with Whitney on synchronized release cadence): one compose per RHIVOS release, same as today; the CDN and ET layers handle the QC LP separation.
  • Distribution / ET: Voyager's ET setup (separate product, separate advisories, Jenkins sync job for -pending tags, CDN layered path /content/dist/layered/...) is the pattern to follow.
  • Schedule: The RHIVOS Release Readiness Meeting of May 20 aligned on tying QC LP versioning and cadence to RHIVOS releases (not independent). This answers Petr's open question on separate Jira releases — not needed.

❌ Where Voyager is NOT the right model (1 critical area)

  • SKUs / access control: Voyager deliberately chose no separate Eng ID and no separate SKU — all RHEL subscribers can access it. Our QC LP requires gated access due to Qualcomm partner/customer agreements. This means we likely need a new Eng Product + separate SKU, which drives the portal/entitlement overhead Whitney flagged in the RHIVOS Release Readiness Meeting of May 20. This is the hardest part and the one that most diverges from the Voyager path.

⚠️ Requires investigation / new work (2 areas)

  • End user tooling / AIB: Voyager is not applicable here — it uses RHEL's build toolchain (Brew/Pungi), not AIB. The RHIVOS pipeline today runs ODCS to produce a single RHIVOS compose, then AIB builds images from it using explicit content.repos URLs — no subscription-manager or librhsm involved. Per Juanje's confirmation, QC LP packages go into the same RHIVOS compose — no separate QC LP compose URL. AIB reads the same compose URL as today; no dual-compose injection is needed. What does need to happen: (1) the Pungi compose config must be updated to include the QC LP Brew tag as an additional koji_tag input; (2) the qcom_repo_url value in targets.yml Jinja2 templates updated to point to the CDN QC LP path instead of COPR (the old per-target .sed file system has already been replaced by Jinja2 in qa.aib.yml.j2 / ps.aib.yml.j2); (3) Jinja2 image manifests verified to pick up the new URL. The open CDN access question is whether the QC LP CDN layered path is accessible to internal pipeline runners before customer entitlement is set up — this needs confirmation with RHELDST.
  • Package gating (Gator / resultsdb / waiverdb / greenwave): Voyager is not applicable here — it uses RHEL's standard gating infrastructure. The RHIVOS pipeline uses automotive/fences/gating/gator for Brew package promotion gating, configured via the GATOR_CONF variable in downstream-pipelines-as-code. The current Gator config covers RHIVOS base packages only. QC LP requires net-new configuration across four layers: (1) a separate Gator config for QC LP packages defining test triggers for Test Console and evaluation/contact-point triggers for package maintainers on gate failure (as specified in the ticket); (2) resultsdb subject associations for QC LP NVRs so test results can be submitted and queried against QC Brew tag content; (3) waiverdb waiver subjects scoped to the QC LP Brew tag, so QC LP waivers do not affect RHIVOS base package gating; (4) greenwave policies for the QC LP Brew tag defining what constitutes a passing gate. TC is image-driven: the pipeline passes TC an explicit image key and S3 paths via tc-cli rhivos create --hw-target ride4_sa8775p_sx — no product discovery from compose or packages. The rhivos token is a fixed TC routing identifier, not tied to image content; QC LP images submit through the same mechanism. QC hardware targets are already handled in the pipeline today. What IS needed: a QC-specific TMT test plan exercising QC audio/video/platform functionality, and new pipeline jobs that build and submit QC LP images with that plan. No new TC product type needed. Contact: Hubert Stefanski (gating).

📝 Architectural note

The RHIVOS Release Readiness Meeting of May 20 discussion suggested Voyager was a poor fit due to build tooling differences (Voyager builds images during compose; RHIVOS builds images after compose via automotive image builder). This is true for the build layer — and for the two-compose design (which was forced by NVIDIA's same-name kernel conflict, not by a general LP requirement). However, Voyager's distribution model (CDN layered path, disabled-by-default repo, separate ET Product + Variant) is directly applicable and exactly what Juanje's proposal ("build internally, separate at CDN") implements. The recommended path: don't adopt Voyager's build tooling or two-compose design, but use its CDN/ET distribution patterns as the reference. One compose, distribution-layer separation.

🔍 Key finding — what the LP work actually is

Review of the custom-images AIB manifest repository reveals that AIB image builds for Qualcomm RIDE4 targets add a supplemental COPR repo via targets.yml Jinja2 templates (the old @ADD_QCOM_BOARD_SUPPORT_*@ sed-file system was replaced by this).

Correction to prior analysis: kernel-ivos-qualcomm, downstream-dtbs, and qcom-scmi are already in Brew under the rhivos-2.0 tag, already Gator-gated (VROOM-37670, completed Q1 2026), and already Errata-onboarded (VROOM-36833, completed Q1 2026), using the rhivos-2-newest-test-pesign build target. The kernel is not a COPR-only package. Whether it also goes behind the QC LP SKU is explicitly TBD (May 20 meeting: “QC kernel (?) — TBD”).

What the Jinja2 templates supply for RIDE4 targets is a supplemental COPR repo owned by the CentOS Automotive SIG (@centos-automotive-sig/qcom-board-support), not by Qualcomm directly. COPR URL: https://download.copr.fedorainfracloud.org/results/@centos-automotive-sig/qcom-board-support/centos-stream-10-$arch/.
Confirmed packages installed from this repo: stmmac-mac-generator (ethernet MAC address generator for the RIDE4 board’s STM32 ethernet controller) and aboot-update (Android Boot updater for QC boards). These are narrow board-specific utilities. The "advance features — QC user space for audio, video" scoped at the May 20 meeting have been verified absent from all ATC-controlled infrastructure — not in this COPR, not in any Brew tag, not in the RHIVOS compose. Note: generic audio/video support (alsa-plugins-pulseaudio, pipewire-*, libcamera-*, gstreamer1-*) is already in the RHIVOS base compose — that is a separate track, not LP scope. The LP is about a QC-specific audio/video stack that does not yet exist as packages anywhere.

The QC LP initiative therefore has two phases: (1) Packaging prerequisite — create the QC-specific audio/video user space packages and get them into Brew under a QC LP Brew tag; this work does not currently exist anywhere. (2) Distribution — once packages exist: QC LP Brew tag as additional koji_tag in Pungi → RHIVOS ODCS compose → CDN layered path behind QC SKU → replace the COPR URL in Jinja2 templates with the LP CDN URL. COPR is public today; the LP is the first formal gate — but the content must be created first.

3-Layer Test Architecture (Benny Zlotnik):

  • Layer 1: Jumpstarter E2E tests on kind clusters (suitable for Jumpstarter)
  • Layer 2: Builder E2E tests on kind clusters (less ideal - Builder is tailored for OpenShift)
  • Layer 3: Black-box integration testing on real OpenShift (RHAS CI - PITCREW-275)
    • Phase 1: Builder + Jumpstarter CI account + ROSA dev cluster
    • Phase 2: In-cluster Jumpstarter with physical boards
    • Phase 3: Upstream E2E tests running on OpenShift

10. RHIVOS vs OpenShift QE Comparison

What RHAS Can Adopt from RHIVOS:

  • Two-phase CTC: Reduced CTC (smoke tests, fast feedback) -> Full ASIL Release CTC (comprehensive validation)
  • Gated promotion with Greenwave: Automated policy evaluation before tag promotion. Removes human bottleneck from go/no-go decisions.
  • WaiverDB discipline: All waivers require BTS links. Prevents "waive and forget" anti-pattern.
  • HiL automation via Jumpstarter: Physical board testing without manual intervention. RHAS already uses this (CTC integration operational).
  • Nightly pipeline with known-issue tracking: Nightly builds catch regressions early. Known issues tracked explicitly rather than silently waived.

What RHAS Can Adopt from OpenShift QE:

  • Four-phase quality strategy: Planning (sizing, Definition of Ready, test plans) -> Development (parallel code + test writing, pre-merge validation) -> Stabilization (EC/RC/GA builds, Component Readiness dashboards) -> Ongoing Maintenance (z-stream, bug escape analysis)
  • Pre-merge vs periodic E2E split: Pre-merge: unit + integration tests (fast, cheap). E2E: run in periodics only (expensive, use sparingly).
  • Component Readiness and Sippy: Release quality monitoring dashboards (OCP uses Sippy for test result trends)
  • Test case management in Jira/Confluence: OCP is migrating from Polarion to Jira/Confluence (PLMORG-249, Suyun leading)

Meeting Context

This was a discovery session, not a decision meeting. Jeff Ligon called it after Summit to collect what's broken or missing in image mode before proposing Bootc as the default for RHEL 11. Two entry points: (1) both automotive and edge were asking about Zstandard Chunked at Summit; (2) Jeff wanted to build a concrete work list around the "bootc by default for RHEL 11" RABU item Scott McCarty owns.

Topics Discussed

1
Zstandard Chunked — missing from RHEL

Both automotive and edge have been asking for this since Summit — it enables faster container pulls on edge/vehicle hardware. It already exists in Fedora but has not been carried into RHEL. Jeff Ligon is actively working to get it plumbed through before it's put in front of customers.

Status: Open, Jeff driving.

2
Developer experience — the central gap

Image mode is a solid deployment model (golden image, consistent fleets, OTA updates). It is a poor development model — locked down, config goes in unexpected places, no clean story for interactive modification.

Ian McLeod (automotive architect) put it plainly: the moment you engage real OEM customers, they need to develop on the system. The current image mode story makes that hard and the automotive/edge teams have been papering over it with "here's a different image for development." That's a muddled story.

Jeff's quick fix idea: Strip the OS tree directory from a Bootc image and you get back to a package-based system. Proposed making this the default RHEL 11 install path — Anaconda installs from a container registry, deletes the OS tree → you're in package mode. Ian: the key requirement is the image must be interactively modifiable and rebuildable, not just a static base.

Status: No committed solution — identified as a primary gap to fix before defaulting to Bootc.

3
Pre-built images — strong consensus

Micah Abbott, Luke Thompson, Ian McLeod all pushed for this. Key data points:

  • Luke (edge portfolio PM): 6 pre-built images would cover ~80% of edge customer requests — HMI, industrial plant floors, kiosks, retail, deterministic workload profiles.
  • Jeff: automotive has the same ARM board fragmentation problem — each board needs specific tuning; universal images haven't fully landed yet.
  • Reference model: Universal Blue / Bluefin — opinionated pre-built image, users kick the tires, then build their own.
  • Andy Burka's counter: pre-built images accelerate time to discovery (get a system up fast without setting up image builder) but don't resolve the developer confusion about how bootc systems work.

Matt Micene's framing: right now we're not meeting the market need — it goes to competitors. Support overhead is the upside problem.

Ian's qualifier: the valuable pre-built image must be one a developer can interactively modify and rebuild — not a static, single-purpose artifact.

4
Anaconda + Bootc graphical installer

Luke Thompson surfaced a filed RFE: install image-mode RHEL via the Anaconda graphical installer — same UX as today but pulling from a container registry instead of an RPM repo. This would make image mode as easy to consume as a standard RHEL install.

Jeff's finding: Justin Cheryl (image mode PO) already built a container that enables this. The work exists. The question is why it isn't prioritized.

Next step: Jeff to document the use case and chase the Anaconda team on prioritization.

5
Staged / canary deployments — known gap, no committed solution

Robert Sturla (Fedora Atomic / Universal Blue) surfaced this as a persistent pain point. No easy way to roll out to a subset of devices, gather feedback, then widen the rollout. Currently: improvise with Ansible, or just ship and hope.

  • Historical reference: Zincotti (Fedora CoreOS update mechanism) had rollout pools and configurable timing — worth revisiting with the CoreOS team.
  • Matt Micene: also a customer need — canary builds + rollback as first-class managed capabilities. Connected this to the Image Builder / managed update story.
  • Jeff: also needed for the hardware lab — segmenting CI/CD devices from kernel dev devices. RHEL Edge Manager is a candidate solution.

Andy Burka's warning: Don't build this as a siloed automotive/edge tool. Prior edge management v1 failed because it wasn't co-located with AAP/ACM/Satellite. Integrate, don't fork.

Status: Gap acknowledged; no committed work item from this meeting.

6
Satellite OCI registry — under-communicated capability

Sean O'Keeffe clarified: Satellite already runs an OCI registry (via Pulp) and can receive pushed container images. This was news to Jeff and likely many others in the room.

Implication: large RHEL customers who already use Satellite to define their RHEL estate (packages, policies, etc.) don't need a separate image registry — the capability is already there. They also don't want to maintain two separate definitions (one for package mode, one for image mode).

Sean committed to sharing a management deck on how RHEL + Satellite + Ansible should work together in the image mode era, and offered a follow-up meeting.

7
Image Builder as "front door" — status and problems

The stated strategy was: Image Builder is the front door to RHEL for all new customers. Problems encountered:

  • Hosted vs. non-hosted Image Builder diverged in functionality.
  • Doesn't solve the traditional Anaconda install path (15+ years of muscle memory).
  • Siloed tools that "look like they should work together but don't quite."

Current direction: fix the divergence, unify the experience, push image mode as the default RHEL path. The Image Builder team is actively working on this.

8
Bootc as default for RHEL 11 — direction set, work list TBD

Scott McCarty has a RABU item: "Bootc by default for RHEL 11." He doesn't yet have a concrete work list for what that means. Jeff is building it.

Dusty Mabe's recommendation:

  • Start with Fedora. The community will surface everything that's broken — but only if you actually promote it, not just leave it in an obscure corner.
  • Engage early and publicly: state intention and direction even without a timeline. Let the community provide feedback.
  • Easy switch back: default image mode install must have a simple one-command path back to package mode — or there will be a revolt.
  • Don't repeat the Hummingbird announcement failure (Scott emailed Fedora Devel 2 weeks before Summit to announce it — felt pre-decided, not community-driven).

Matt Micene: right direction, but there are "pretty big pitfalls" in current onboarding — fix those before shipping as a default.

9
CoreOS + Bootc unification — stalled, worth revisiting

Dusty mentioned a working group from last year that explored whether CoreOS and Bootc should collaborate or merge. It stalled. He suggested it's worth trying to restart those discussions.

Implication: If CoreOS and Bootc converge, it could significantly shift the foundation both systems build on.

10
ELN build of Bootc

Jeff is co-maintaining an ELN (Extra Packages for Enterprise Linux Next) build of Bootc with Steven Gallagher. Primary goal: use Bootc as the delivery mechanism for Anaconda — if it works, Neil (GMPA) is interested in backing it as a first-class Fedora path. This is the upstream groundwork for the Fedora-first strategy.

Impact on RHIVOS & RHAS

Direct & Significant

High impact

Developer story gap — barrier to OEM customers

Ian McLeod (automotive architect) named this explicitly: once real OEM customers engage, they need to develop on the system, not just deploy. RHIVOS is deploy-great, develop-terrible. No solution was committed — it's the primary gap blocking Bootc-by-default.

High impact

Canary / staged deployments — automotive stakes

Higher stakes than anywhere else: you can't blindly push an unchecked update to a vehicle fleet. No first-class tooling exists. RHEL Edge Manager is a candidate but nothing is committed. Open gap directly affecting RHIVOS fleet operations.

High impact

Zstandard Chunked — automotive explicitly waiting

Jeff flagged this as a priority for automotive (alongside edge). Exists in Fedora, not in RHEL. RHIVOS needs it for faster container pulls on vehicle hardware. Jeff is actively driving.

High impact

Bootc as RHEL 11 default — ecosystem effect

RHIVOS is already bootc-based. If RHEL 11 ships a good developer story and pre-built images, it strengthens the ecosystem RHIVOS lives in. If it ships with current gaps as a "default," OEM first impressions will be negative and associated with RHIVOS.

Medium impact

Pre-built RHIVOS board images not yet delivered

Jeff acknowledged each ARM board needs specific tuning. No automotive-specific pre-built images exist yet. Strong consensus that these are needed to reduce OEM onboarding friction. Must be interactively modifiable, not static.

Medium impact

Satellite OCI registry — untapped for RHIVOS fleet

Satellite already supports bootc container push via its OCI registry (Pulp). If RHIVOS fleet management uses Satellite (as large RHEL customers do), this capability is available and avoids building a parallel solution. Sean's management deck will have details.

Medium impact

Tool integration caution (Andy Burka)

Any automotive-specific deployment tooling built for RHIVOS must integrate with Satellite/Ansible/ACM — not stand alone. Prior edge management failure is the cautionary tale. Direct architectural guidance for RHIVOS-related tooling decisions.

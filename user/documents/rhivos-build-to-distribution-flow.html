Overview End-to-End Pipeline (6 Phases)

The RHIVOS release pipeline flows through six major phases. Each phase involves specific tools, Brew tags, and automation. The pipeline is largely automated via GitLab CI (downstream-pipelines-as-code) with Gator handling gating decisions.

Detail Detailed Pipeline Stages

The downstream pipeline (downstream-pipelines-as-code) orchestrates 27 stages via GitLab CI. The three-layer inheritance model (upstream AutoSD base, enterprise overrides, release-specific config) enables one pipeline to serve multiple release streams.

1. Source Code Commit

Maintainer pushes to the appropriate dist-git branch. Dist-git server-side hook (gitbzverify) enforces Jira ticket references for GA-phase branches.

dist-git pkgs.devel.redhat.com
BranchReleasePolicy
rhivos-2-mainRHIVOS 2.1 (dev)No restrictions
rhivos-2.0RHIVOS 2.0 GA / 2.0.zStrict: VROOM ticket + fixVersion + blocker approval
Exceptions: kernel-automotive, kernel-ivos-qualcomm, downstream-dtbs, qcom-scmi have "Anything Goes" on rhivos-2.0 (source-git workflow; gating happens upstream). kernel-ivos-nxp-extra-modules was missed and needs a RHELBLD ticket.

2. Brew (Koji) Build

Maintainer triggers a build using rhpkg build --target. The build target determines which Brew tag the build lands in.

ReleaseTargetDestination Tag
RHIVOS 2.0 GA--target rhivos-2.0-candidaterhivos-2.0-gate
RHIVOS 2.0.z--target rhivos-2.0-z-candidaterhivos-2.0-z-gate
RHIVOS 2.1--target rhivos-2.1-candidaterhivos-2.1-candidate
Brew/Koji rhpkg Kerberos
Buildroot: Uses rhivos-X.Y.Z-build tag as the buildroot (stable, gated content). New builds land in -gate, not immediately visible to subsequent builds. The STAG proposal (not yet implemented) would allow lockstep builds of interdependent packages.

3. Tagging into -gate

Builds are tagged into the -gate tag using brew tag-build. This is the entry point for Gator evaluation.

brew tag-build rhivos-tagger permission
Known gap: Ownership for who tags packages into -gate is not formally documented. In practice: some maintainers request tagging via Sameera Kalgudi; for RC scenarios, Francisco da Rocha and Ozan Unsal do it ad-hoc. Kernel maintainers (Oleksii Baranov's team) lack rhivos-tagger Brew permission. RHELBLD-18777 and RHELBLD-18778 filed to extend permissions.

4. Gator Evaluation (Package Gating)

Gator is a stateless Python CLI that automates RPM evaluation and promotion. It diffs source vs. target Brew tags, evaluates new packages against Greenwave policies, and checks ResultsDB for test results.

  • Pass: Auto-promotes to -candidate tag
  • Fail: Posts Slack notification with WaiverDB links for manual waiver
  • kernel-automotive special path: Checks ReportPortal for triage status; if all failures have BTS links, auto-promotes
Gator Greenwave ResultsDB WaiverDB ReportPortal

5. Release Config & Pipeline Trigger

A release config file (.gitlab/release-configs/RHIVOS-X.Y.Z-RCn.yml) is created in downstream-pipelines-as-code. A git tag on the rhivos repo triggers the GitLab CI pipeline.

BUILD_BRANCH is the master switch. It loads the corresponding release config which sets STREAM, X_STREAM, Y_STREAM, compose URLs, Koji tags, and S3 paths.

downstream-pipelines-as-code release-definitions GitLab CI
Three-layer inheritance: Layer 1 (upstream AutoSD base) - Layer 2 (enterprise overrides + extensions) - Layer 3 (release-specific config loaded FIRST). Include order in .gitlab-ci.yml is critical: wrong order breaks variable resolution.

6. ODCS Compose Generation (generate-compose)

ODCS (On Demand Compose Service) generates an RPM repository from the Pungi config and the -candidate Brew tag. The compose defines the bill of materials for the RHIVOS release.

Duration: 10-30 minutes. Requires Kerberos auth via KEYTAB_ODCS. Packages must be signed; unsigned packages cause ODCS rejection.

ODCS pac-jobs generate-compose Pungi

7. Repository Closure Check (check-repoclosure)

Validates that all RPM dependencies in the compose can be satisfied. Catches broken dependency chains before image builds start.

pac-jobs repoclosure

8. Image Build (build-*-image)

Automotive Image Builder (AIB) builds OS images from the compose repos. Image recipes define how to assemble images per hardware target. The compose URL is passed as a repo source in the AIB manifest (content.repos).

Thin executor pattern: pac-jobs pre-computes all build parameters (AIB_COMMAND, S3_UPLOAD_PREFIX, BUILD_FORMAT). create-osbuild executes inside a container, resolves manifests from custom-images repo, runs AIB/OSBuild, uploads artifacts to S3.

AIB create-osbuild pac-jobs build-image Testing Farm AWS S3
FormatTarget
qcow2QEMU / VM testing
abootAndroid Boot (Qualcomm boards)
simgSparse image (ebbr/TI/Renesas boards)
AMIAWS cloud images
Key difference from RHEL-for-NVIDIA: RHIVOS builds images AFTER the compose (compose first, then AIB). RHEL-for-NVIDIA builds images DURING compose time (via Pungi/ODCS). This is an architectural incompatibility that makes Voyager's build tooling inapplicable to RHIVOS.

9. Smoke Tests (smoke-tests-*)

Hardware smoke tests run on physical boards via Test Console. pac-jobs submits tests with deferred report uploads (disables TC upload jobs at submission; batch-enables after all pass to prevent partial uploads).

10. Confidence Test Cycle (CTC)

For release candidates: formal CTC runs with broader test coverage. Includes kernel gating, systemd, a-b-c tests, kselftests, LTP. Results feed into release go/no-go decision.

Two phases for RC builds: Reduced CTC (day 1 - smoke + kernel gating), Full CTC (weekend - ASIL-B + kernel debug for FuSa evidence).

Test Console ResultsDB Polarion

11. Compose Promotion (promote-compose)

After testing passes, the compose is promoted. pac-jobs runs promote-compose via SSH to the RCM host with Kerberos/GSSAPI auth. ComposeDB import registers the compose for downstream consumption.

Gator runs promote-packages-in-brew to move packages from -candidate to -pending.

pac-jobs promote-compose RCM Host ComposeDB Gator promote

12. Errata Advisory Creation

Gator's generate-advisories command scans passing packages, searches for matching VROOM Jira tickets, creates advisories in Errata Tool, and attaches builds. Separate FuSa and Core batches are maintained.

  • Attaches only Stories and Bugs for RHIVOS packages
  • Jira tickets become customer-visible release notes
  • RHEL-derived advisories are cloned and adapted by Marcel (RHEL issue keys placed as URL references to avoid cross-project comments)
  • Multicomponent advisories can bundle kernel + derivatives
Gator generate-advisories Errata Tool Jira

13. Package Signing

Signing happens automatically when builds are attached to errata advisories. The Errata Tool triggers PQC (Package Signing Certificate) signing on attachment. No manual signing step needed - but builds must be in -candidate tag first (gating must pass).

Errata Tool PQC

14. CDN Push (REL_PREP to Live)

Errata advisory pushed to CDN-stage for validation, then to production CDN. RPMs via Errata Tool/Pub. ISOs/QCOW2 images via Pub separately. Nightly/latest builds promoted via CloudFront invalidation.

CDN paths follow the pattern: /content/dist/rhivos2/2.0/$basearch/os

Pub Akamai CDN AWS CloudFront

15. Customer Access

Customers access RHIVOS content via entitled subscriptions. The CDN Authorizer (edgejava/edgecert at Akamai edge) validates both the entitlement certificate (covers content set) and the Product ID certificate (installed product).

subscription-manager Candlepin CDN Authorizer

Streams Nightly vs. Release Pipeline

The same pipeline serves both nightly rolling builds and frozen release candidates. BUILD_BRANCH selects which release config to load.
Nightly (Rolling)

Config: latest-RHIVOS-2.0-Core, latest-RHIVOS-2.0

Triggered on schedule. Picks up whatever is in -candidate tag. Composes, builds images, runs smoke tests. Published to rhivos.auto-toolchain.redhat.com.

Promotion: Nightly/latest builds promoted via CloudFront invalidation (STS AssumeRole).

Release Candidate (Frozen)

Config: RHIVOS-2.0-Core-RC3, RHIVOS-2.0-RC3

Triggered by git tag on rhivos repo. Uses pinned package versions. Full CTC cycle. Results feed go/no-go decision.

Promotion: Compose promoted via SSH to RCM host. ComposeDB import. Errata advisories pushed to CDN.

Distribution Errata to CDN Chain

The ATC Distribution pipeline handles everything from advisory creation to CDN delivery. Documented in the ATC Distribution FA wiki (Confluence page 402130012, 10+ pages).

Advisory Creation

Gator generate-advisories finds passing packages in -candidate tag, checks for existing advisories in NEW_FILES state, creates or updates advisories in Errata Tool with VROOM Jira issue links.

FuSa (batch 4254) and Core (batch 4576) batches are separate and must never be cross-contaminated.

Build Attachment & Signing

Builds attached to advisories via Gator. Errata Tool triggers PQC signing on attachment. Jenkins job syncs -pending Brew tags.

Verification via errata-distribution scripts: fetch_batch_builds.py, compare_batch_compose_repos.py, sync_batch_compose_builds.py.

Product Listings

Product listings map RPMs to Errata Tool products (which RPMs appear under which product version). Generated from compose via pac-jobs create-product-listing on the RCM host.

Known issue: PLM auto-generates listings from Brew build contents, not compose trees. This causes ghost entries (e.g., cross-binutils debuginfo appearing for architectures not in the RHIVOS compose). Overrides needed per occurrence.

CDN Push

Advisory transitions: QE → REL_PREP → PUSH_READY → IN_PUSH → SHIPPED_LIVE. RPMs pushed via Pub to CDN repos. Images (qcow2, ISO) pushed separately.

CDN repos: /content/dist/rhivos2/2.0/$basearch/os (Core), /content/dist/rhivos2/2.0-core/$basearch/os

Jira Ticket Closure

VROOM tickets in Release Pending transition to Closed automatically when content is pushed to CDN. No manual action needed.

Future RHIVOS on GitLab Migration (Planned)

RHIVOS is being transitioned to GitLab (RHEL on GitLab / RoG pattern). This will change the build-to-gate flow significantly. AUTOBU-1105, top team priority alongside CAIB and Konflux.
Current Flow
  • Direct pushes to dist-git branches
  • Branch gating via dist-git policy rules
  • Real builds land in -gate tag
  • Gator + ResultsDB + Greenwave for evaluation
  • One build at a time through gate
  • No formal audit trail
Target Flow (GitLab)
  • Merge request workflows with reviews
  • MR-based gating via GitLab CI / OSCI pipelines
  • Draft builds in Brew (promoted to real on MR approval)
  • Grouped builds tested and promoted together
  • Full auditability (reviewer on every change)
  • Bypasses current -gate tag (draft builds go to -candidate)
Impact on current flow: The RoG draft tagging process bypasses the current -gate flow. Gator's role would be replaced by OSCI pipelines and a small GitLab job for -pending to -candidate promotion. 21 packages identified for onboarding. 4-phase migration planned Jul 2026 - Feb 2027.

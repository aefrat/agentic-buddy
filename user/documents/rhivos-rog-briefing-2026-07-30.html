Key Findings from the Meeting

1. Scope: ~30 RHIVOS-specific packages only
Additional RHEL package testing (where RHIVOS runs extra tests on RHEL packages) is out of scope for this initiative. It runs separately, later in the pipeline. RHIVOS stays in the private GitLab namespace (Red Hat employees only). CentOS Stream sync is not on the agenda.
2. Dynamic main branch - solvable, needs custom work
RHIVOS manages its own main branch that shifts as releases evolve (rhivos-2-main becomes rhivos-2.2 when 2.1 releases). Draft builds from MRs need to dynamically resolve the correct Brew target. RHEL doesn't have this issue (CentOS Stream handles versioning). Michal confirmed Voyager has a similar situation and it's solvable.
3. GitLab and dist-git are separate storage systems
Not a frontend on dist-git - they're completely separate systems that sync bidirectionally. Dist-git remains the source of truth (lookaside cache). BC check runs as an MR test in GitLab. Petr wants GitLab-only (disable direct dist-git pushes). Michal says this is preferable and easier for smaller teams who can mandate it to all maintainers.
"If RHIVOS is smaller and you can actually talk to all the maintainers and tell them 'you are onboarded to GitLab, please don't push directly to dist-git' - then that would be great." - Michal Srb
4. Conflux deferred - build in Brew first
Conflux integration requires workspaces and application component models - takes significant time. Build in Brew initially. When Conflux team has capacity, the switch should be invisible to maintainers. Lookaside cache support for building directly from GitLab is still WIP (specific Conflux feature work in progress). Deferred
5. Testing: phased approach with existing gating as safety net
Michal proposed an incremental migration. RHEL testing is also "kind of messy" with 13+ Jenkins instances and teams migrating at different speeds. Adding RHIVOS-specific logic is "always possible." Juanje described the current RHIVOS testing stack: centralized TMT plan repo, Test Console as orchestrator, routing to Testing Farm (VMs) or Jump Starter (bare metal/edge).

Testing Migration Phases (proposed by Michal Srb)

Phase 1: Onboard without tests
MR merge -> build lands in -gate tag -> existing Test Console gating continues as-is. All current testing infrastructure untouched.
Phase 2: Plug tests into MRs
Figure out how to run RHIVOS tests within merge requests and provide results in the MR UI. Tests validate draft builds before merge.
Phase 3: Skip old gating
When MR merged, draft build promotes directly to -candidate. Old gating (Gator + Test Console promotion flow) replaced entirely.
6. GitLab-native sidetag workflow - top OSCI priority
Current Jenkins-based sidetag workflow won't work for RHIVOS. Adam's team is building a new GitLab-native version for RHEL as a top priority. Should be reusable for RHIVOS "without any changes." This solves the kernel team's daily pain point: daily kernel builds + external kmod sidetag rebuilds, currently all manual.
"That would be fantastic because that's currently a huge pain point especially for the kernel team. They build a new release every single day but we also have external kmods that need to be built against that kernel." - Petr Sabata
7. Configuration readiness
OSCI uses box-law-data components repo as source of truth for onboarding. RHIVOS already has entries there with default assignees and contributors. One human approver policy matches RHEL's configuration. This prerequisite is effectively met. Ready

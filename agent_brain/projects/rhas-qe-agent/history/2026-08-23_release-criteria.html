Introduction

This document defines measurable pass/fail conditions for each RHAS release milestone. It answers the question: "What must pass before this release can ship?"

IMPORTANT: These criteria are recommendations based on RHIVOS CTC patterns and OpenShift Quality Strategy. PITCREW-337 (QE Readiness) is the official epic defining release criteria - it is currently unassigned with 0 comments after 3+ months. Formal adoption requires QE lead assignment and stakeholder approval.

Criteria Tiers:

  • Monthly Release (RHAS-MMYY): Baseline quality for monthly iterations
  • Tech Preview (RHAS-0926, Sep 29): Superset of Monthly + customer-facing readiness
  • GA (RHAS-1226, Dec 22): Superset of Tech Preview + production-grade validation

Waiver Process

Purpose: Controlled mechanism for shipping with known gaps when business justification exists.

Waiver Requirements:

  • Authorization: Product Manager (Paul Wallrabe) + QE Lead (currently unassigned) joint approval required
  • Documentation: Jira ticket filed with:
    • Impact assessment (what breaks, who's affected)
    • Timeline to fix (specific date or release)
    • Customer impact analysis (workarounds available?)
    • Risk mitigation plan
  • Tracking: Waiver ticket linked to release version in Jira
  • Limits: Maximum 3 waivers per GA release
  • Non-waivable: Critical CVEs, zero blocker bugs (GA-09)

RHIVOS Pattern: Waivers tracked in WaiverDB with mandatory BTS links. No silent waivers - all require explicit justification. RHAS should adopt this pattern when formal QE process is established.

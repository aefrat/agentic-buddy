### Session 2: Release blocker agent data correctness bug

## Decisions
- Identified root cause of VROOM-46538 appearing in all 3 release reports (rhivos-2.0, rhivos-2.0.z, rhivos-2.1) when it should only appear in rhivos-2.0.z. Two contributing factors:
  1. **Primary:** `cross_reference_tickets()` in `synthesize.py` (lines 30-162) merges ALL Slack `ticket_activity` entries without any release filtering. Any ticket mentioned in Slack but not a Jira blocker for a given release shows up as "discussed in Slack but not tracked" for ALL releases.
  2. **Secondary:** `startswith` prefix matching in `compute_stats.py` at 3 locations (lines 179-180, 351-352, 417-419) causes "rhivos-2.0.z".startswith("rhivos-2.0") to match, incorrectly attributing 2.0.z tickets to 2.0.
- Proposed 3-part fix (not yet implemented):
  1. `synthesize.py`: Pass `untracked_lookup` into `cross_reference_tickets`, filter Slack-only tickets known to belong to other releases before including them.
  2. `agent.py`: Pass `untracked_lookup` dict to `synthesize.run()` (currently only passed to `compute_stats.run()`).
  3. `compute_stats.py`: Replace `startswith` with exact match in 3 locations.
- Verified via cached HTML output that meeting notes did NOT contribute to the leak (all three releases show "No VROOM tickets referenced").

## Lessons
- **GitLab events API systematic gap discovered:** `/users/{id}/events?action=merged` only returns MRs where the user clicked the merge button, not MRs they authored that someone else merged. Matt Goldman's MR !854 (product-service-config-auto, merged Jun 15 by `mhaluza`) was invisible to the collection method. This affects all team members' QC data - authored MRs merged by others are systematically missed.
- The correct query for complete MR coverage must combine: (1) events API for MRs the user merged themselves, and (2) `/merge_requests?author_username=X&state=merged` for MRs they authored that others merged.

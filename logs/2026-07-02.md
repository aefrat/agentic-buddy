## Lessons
- SBI framework works well when the positive intent is acknowledged within the Behavior section rather than as a separate softener - it makes the feedback feel more integrated and less like a "compliment sandwich."
- When constructing SBI feedback iteratively, new information from the recipient's perspective can fundamentally shift the core issue. Kanitha's clarification (she did ask permission) meant the problem wasn't about sharing - it was about the precision of language. The lesson: don't lock in the SBI framing too early; be ready to rewrite the Behavior section entirely when you learn the other side's account.
- gws drive files create requires `--upload` flag (not `--media`) for file upload with `--upload-content-type` for MIME type. For HTML-to-Google-Docs conversion: metadata (name, mimeType) must go in `--json` (request body), not `--params` (URL params). Using `--params` for mimeType uploads raw HTML; using `--json '{"name": "...", "mimeType": "application/vnd.google-apps.document"}'` triggers conversion to native Google Docs format.
- Gmail send with large HTML attachments can exceed shell argument list limits. For large attachments, either send as separate emails or use Drive links instead of inline attachments.

## System observations
- **Concept candidate:** "Policy enforcement vs process requirement separation" - dist-git policy enforcement (server-side commit hooks) and errata ticket requirements (advisory generation) are independent systems that address different concerns. Disabling one doesn't remove the need for the other. Generalizable: any automated enforcement gate that gets disabled still leaves the business process requirement intact. The automation just makes it mandatory; without it, the requirement becomes tribal knowledge and gets missed.

This session spawned 6+ parallel agents across phases. Could generalize into a "create agent from requirements" meta-skill. (seen: 1)
- **Concept candidate:** "Three-tier progressive criteria model" - each release milestone is a strict superset of the previous one, with measurable pass/fail conditions per criterion. Adapted from RHIVOS CTC (two-phase: Reduced then Full) and OCP (EC/RC/GA builds). ## Lessons (Session 6)
- Non-interactive `claude -p` calls need `--dangerously-skip-permissions` to write files. Without it, Claude prompts for permission which can't be granted in cron/script context, causing silent failures (writes don't happen, no error exit).
- Two-step automation with a manual second step is effectively a one-step automation. If step 2 requires human remembering, it will be forgotten. The 11-day staleness of repo-wiki/ files proves this. When automating a pipeline, either automate all steps or accept that unautomated steps won't happen reliably.

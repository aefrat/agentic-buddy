## Context

- **Paul Wallrabe asked** (via Slack DM): "Hey Avihai, qq: would it make sense to run autosd nightly tests on jumpstarter directly?"
- Researched across Distribution FA LLM wiki, agent brain project files, and Slack to build a comprehensive answer.

### Key findings

1. **AutoSD upstream nightly pipeline builds images but only tests on QEMU VMs, not real hardware.** Juanje confirmed in #team-toolchain-automotive: "we don't test the board ones for AutoSD, we don't have access from the upstream pipeline to the boards." The upstream pipeline runs on GitLab CI via Testing Farm VMs with no network path to the Jumpstarter board cluster.

2. **This is not a deliberate decision - just infrastructure never wired up.** The boards serve RHIVOS downstream pipelines. Roderick Kieley noted there's "1 internal lab supporting RHIVOS developers" and "1 cluster upstream for CentOS community" - neither connected to the upstream nightly CI.

3. **The gap has real cost.** Ozan flagged on Jul 31 in #team-cats-automotive that kernel-automotive-6.12.0-251 issue on Ride4 boards was only caught downstream because "AutoSD is not tested on real HW." The same kernel version caused the RHIVOS 2.1 nightly to fail (disk_full during kernel module signing - root cause was a broken msm_hab.ko module inflating to 2.6GB).

4. **Feasibility is high.** People already manually flash AutoSD nightly images on Jumpstarter boards (Dustin, Benny, sdoherty, Patricia, nsednev in #forum-jumpstarter). The test_images_info.json resolver is consumed by Jumpstarter tooling. Luigi's switch from Testing Farm to Jumpstarter for RHIVOS was highlighted as a success in the 2.0 retro.

5. **Capacity is the main concern.** June had lease starvation (all 7 exporters occupied) traced to a Python 3.14 TMT cleanup crash leaking leases. Adding upstream nightly runs to the same pool needs planning.

### Decisions

### Tasks captured

### Context

- User asked to learn about [agentbehavior.dev](https://www.agentbehavior.dev/) (Braintrust + Basis open standard) and connect it with Agent-forge.
- Researched the site, GitHub repo ([braintrustdata/agentbehavior](https://github.com/braintrustdata/agentbehavior)), and Braintrust blog post.
- Cross-referenced with existing Agent-forge design principles file.

### Key findings

1. **Agent Behavior Specs are the evaluation layer Agent-forge lacks.** Agent-forge builds the harness (identity + memory + skills + permissions). Behavior specs define what good conduct looks like and grade it (true/false/NA) against recorded trajectories.

2. **Strong alignment with Agent-forge principles:**
   - Disconfirmation gate maps to Evidence dimension (verify before deciding)
   - Episodic memory store produces the traces that behavior specs judge
   - "Tool output > instructions" parallels specs' core distinction (specs describe what should happen, not how)
   - Permissions as design + Failure modes both constrain the behavioral envelope

3. **Key design philosophy:** "Expect to remove prescription over time, not accumulate it." Retire specs for behaviors models reliably exhibit. This aligns with Agent-forge's thesis that the harness is the durable investment.

4. **Spec format:** BEHAVIOR.md with YAML frontmatter (name + description) + Markdown body using 6 optional dimensions (Intent, Evidence, Decision, Execution, Recovery, Failure modes). Lives in `.agents/behaviors/<name>/`.

5. **When to write a spec:** Frequent + High-impact + Agent-defining + Ambiguous-by-default + Spread-across-context + Useful-for-debugging. "Elevate the few you care about enough to measure."

### Ideas

- Behavior specs could be written for agentic-buddy's existing rules that have caused the most friction (no-unsourced-content, memory-before-external-lookup, commit-after-capture). The observations journal is essentially a proto-evaluation log - it already tracks behavioral regressions. Connecting it formally to behavior specs would close the loop.

> The 7 principles that behavior specs would evaluate against - especially P5 (Skill Design) and P6 (Memory Architecture).

### Key findings

1. **Google Docs dateElement smart chips are invisible to naive text extraction.** The text extraction function only handled `textRun` elements, silently dropping `dateElement` (date smart chips) and `richLink` (linked URLs). The release readiness doc uses date smart chips as weekly separators - without extracting them, the entire post-March-2025 content (95K chars) appeared as one undated blob labeled "Current."
2. **Meeting notes need domain-aware filtering.** A general meeting doc discusses everything (testing, licensing, schedules, blockers). Keyword-based filtering ("safety", "security", "CVE") catches too much non-blocker content. Ticket-based filtering (any VROOM reference) catches non-blocker tickets discussed for other reasons. Only cross-referencing against the actual Jira blocker set produces useful results.
3. **VROOM-47482 false positive journey:** Appeared 3 times as a false positive before being eliminated. (a) First as "Blocker Mention" via 80-char context window near a CVE keyword, (b) then as a line containing a VROOM key, (c) finally as a "potential blocker" because someone added test text containing the word "blocker". The final cross-reference filter catches (a) and (b); (c) is intentionally kept because the doc explicitly says "blocker."

### Lessons

- **Iterative dashboard review beats specification.** The user's review cycle (run agent -> open dashboard -> spot problems -> request fix) produced better requirements than an upfront spec would have. Each iteration surfaced problems that weren't visible until real data was rendered. Five rounds of "this looks wrong" converged on the right behavior faster than trying to specify it formally.
- **Google Docs API element types are richer than textRun.** A paragraph's `elements` array can contain `textRun`, `dateElement`, `richLink`, `person`, `autoText`, and others. Any text extraction that only handles `textRun` will silently lose content. Must enumerate all element types.

### System observations

- **Concept candidate:** "Google Docs dateElement smart chips invisible to text extractors" - Google Docs paragraphs can contain `dateElement` (date smart chips), `richLink`, and `person` element types alongside standard `textRun`. Text extraction functions that only handle `textRun` silently drop these, producing text with invisible gaps. The release readiness doc had 64 date smart chips acting as section separators that were completely invisible. Detection: any doc where meeting count or section count is unexpectedly low, check for non-textRun elements. Fix: enumerate `dateElement.displayText`, `richLink.richLinkProperties.title/uri`, `person.personProperties.name`. (seen: 1)
- **Concept candidate:** "Domain-set cross-referencing for content extraction" - when extracting relevant content from a general-purpose source (meeting notes, Slack, email), filter against the specific domain data set (known Jira blockers) rather than keyword heuristics. Keywords produce false positives (any mention of "safety" near a ticket key) and false negatives (blockers discussed without using the word "blocker"). Cross-referencing against the authoritative source eliminates noise. Applied: meeting notes filtering against `all_statuses_data` blocker keys. Generalizable to any "extract X from mixed-content source" problem. (seen: 1)

- User asked educational questions about ADC token renewal, thinking model budgets, and Vertex AI authentication patterns.

### Key findings

1. **Claude Code's GCP project is not usable for direct API calls.** The project `itpc-gcp-core-pe-eng-claude` is provisioned exclusively for Claude Code's internal infrastructure. Publisher model endpoints (both Anthropic and Google) return 404. This was tested across multiple regions (us-east5, global, us-central1, europe-west1, europe-west4) and model name formats.
2. **ADC tokens auto-renew.** Application Default Credentials use a refresh token that persists in `~/.config/gcloud/application_default_credentials.json`. The SDK transparently exchanges it for short-lived access tokens (1 hour). No manual renewal needed unless the refresh token is revoked or unused for ~6 months.
3. **Thinking models need explicit budget control for simple tasks.** Without `thinking_budget=0`, Gemini 2.5 Flash consumed 96% of the output token budget on internal reasoning for a 3-5 sentence synthesis task. The thinking is invisible in the response but consumes the same token pool as visible output.

### Lessons

- **Check available GCP projects before assuming model access.** `gcloud projects list` and `gcloud services list --enabled --project=<id>` quickly reveal which projects have Vertex AI enabled and which models are accessible. The Claude Code project was a dead end; the purpose-made project worked immediately.
- **Thinking model defaults are designed for complex reasoning tasks.** For simple synthesis (summarize structured data into prose), thinking overhead is pure waste. The `thinking_budget` parameter exists specifically for this use case - disable or limit thinking for straightforward generation.

### System observations

- **Concept candidate:** "Thinking model token budget trap" - thinking models (Gemini 2.5 Flash, Claude with extended thinking) consume output tokens for internal reasoning. A 500-token budget can produce only 19 visible tokens if the model spends 477 on thinking. For simple tasks (summarization, synthesis, classification), disable thinking entirely (`thinking_budget=0`). For complex tasks, increase `max_output_tokens` proportionally to expected thinking overhead. The trap is that the model appears to work (no error) but output is truncated to near-zero. (seen: 1)
- **Concept candidate:** "Vertex AI dual-mode SDK pattern" - the `google-genai` SDK supports both API key mode and Vertex AI (ADC) mode via the same `Client` constructor: `genai.Client(api_key=key)` vs `genai.Client(vertexai=True, project=id, location=region)`. Code can check for `GOOGLE_API_KEY` first (free-tier/personal), fall back to `VERTEX_PROJECT_ID` (enterprise/ADC). Same model names, same generation API, different auth paths. Pattern for building LLM tools that work across personal and enterprise environments. (seen: 1)

### Session 4: RC3 Slack follow-up + RHIVOS release process deep dive

#### Decisions

- None — research/analysis session clarifying RHIVOS release mechanics.

#### Context

- **Re-scanned #automotive-release-readiness** (June 11). 2 new messages:
  - Kanitha confirmed `kernel-ivos-nxp-extra-modules` is NOT a subpackage of kernel-ivos — built independently via CBS/Brew. Mattijs Korpershoek pointed to [RHICIL-45](https://redhat.atlassian.net/browse/RHICIL-45). Because it's independent, it **needs its own errata advisory** with NVR attached. Mattijs doesn't know how — Enric/Francisco must do it.
  - Kanitha gave RC3 trigger condition: "as soon as all packages in candidate tag, attached to errata and got signed we can trigger RC3. Best case, pipeline would finish in few hours."
- **Deep dive into RHIVOS Brew tag structure.** Read actual Gator configs (`RHIVOS-2.0-gating.yaml`, `RHIVOS-2.0-Core-gating.yaml`, `errata-2.0-config.yaml`, `errata-2.0-core-config.yaml`). Key findings:
  - Both FuSa and Core share **one gate tag** (`rhivos-2.0-gate`) and **one candidate tag** (`rhivos-2.0-candidate`). The FuSa/Core distinction happens at errata level (batch `RHIVOS-2.0.0` vs `RHIVOS-2.0.0-Core`).
  - `kernel-ivos-qualcomm` has `depends_on: [downstream-dtbs, qcom-scmi]` — those must be in `-gate` before kernel-ivos-qualcomm can pass.
  - `kernel-automotive` and `kernel-ivos-qualcomm` have `ignore_failure: false` — must pass gating or be waived. Contact: `sbertram`.
  - `kernel-ivos-nxp-extra-modules` IS listed in both errata configs' package lists — Gator's `generate-advisories` will handle its advisory automatically once it passes gating.
- **Clarified: tagging and errata are decoupled steps.** Read Gator's `generate_advisories.py` source code. `gator evaluate` (tag promotion to `-candidate`) and `gator generate-advisories` (errata attachment) are separate CLI commands, not atomic. Errata attachment happens after `-candidate`, not simultaneously. Also found a workaround in the code: FuSa gate check is currently skipped (`# At the moment, fusa gate still failed so skipping`), so `generate-advisories` processes all in-scope packages regardless of Greenwave pass status.
- **Signing is not documented** in any of the three repos. The Voyager comparison doc says "signing happens immediately on attachment (PQC signing)" for the NVIDIA flow. For RHIVOS, kernel signing is "Not documented separately." Most likely: ET infrastructure handles RPM signing automatically when builds are attached to advisories.
- **No documented owner for initial `-gate` tagging** confirmed across all three repos. The wiki says "maintainer builds land in `-gate`" but doesn't name who or how for RC scenarios with pre-existing builds.

#### Lessons

- **Gator configs are the source of truth for tag names and package scope** — not the wiki or CLAUDE.md docs. The actual YAML files in `gator/config/RHIVOS-2/` have the exact tag names, package lists, contacts, and `ignore_failure` flags. Always read these first when answering tag/errata questions.
- **`generate-advisories` currently bypasses Greenwave** for FuSa packages (code comment). This means errata advisory creation doesn't actually depend on gating passing — it processes all in-scope packages. Important to know when reasoning about the RC3 sequence.

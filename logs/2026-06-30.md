## Session 31: autosd.sig.centos.org certificate expiration diagnosis

### Context
- Eric Chanudet reported (Jun 29) that `autosd.sig.centos.org` serves SEC_ERROR_EXPIRED_CERTIFICATE. Reported in `#team-product-automotive` (C06794HLMLK) and `#team-cats-automotive` (C065UN1CVL7). Pingou confirmed the Toolchain team maintains this and tagged the user.
- This is the 4th certificate expiration on the same host: Oct 2024, Dec 2025, Mar 2026, Jun 2026. Let's Encrypt cert expired Jun 29, 2026 at 18:25:32 GMT. The 90-day cert cycle keeps failing silently.
- Hubert (hstefans) set up ACME cert automation via cert-manager on the MP+ OpenShift cluster (`mpp-e1-prod`) in Oct 2024 (MR 284). He's on PTO today.
- The user already messaged Eran and Matt in `#only-toolchain-allowed` but no response yet.

### Decisions
- Investigated the root cause live on the MP+ cluster rather than waiting for Toolchain team availability.

### Root cause identified
The cert-manager ACME HTTP-01 renewal fails every cycle due to an **OpenShift ingress-to-route incompatibility**:
1. cert-manager creates an Ingress resource with `pathType: Exact` for the ACME challenge path (`/.well-known/acme-challenge/<token>`)
2. OpenShift's ingress-to-route controller does NOT support `pathType: Exact` - only `ImplementationSpecific` and `Prefix`
3. The controller emits `IncompleteIngressToRouteRules: Unsupported exact path type` but **silently skips route creation**
4. The solver pod runs, the solver service exists, but with no Route, Let's Encrypt's HTTP-01 validation hits the main webserver route and gets 404
5. The CertificateRequest stays in `READY=False` / `Pending` indefinitely

Key diagnostic evidence:
- `oc get certificaterequest`: Approved=True, Ready=False, 30 days old
- `oc describe challenge`: `Reason: Waiting for HTTP-01 challenge propagation: wrong status code '404', expected '200'`
- `oc get events`: `IncompleteIngressToRouteRules` on `ingress/cm-acme-http-solver-m8wqz`
- Solver pod `cm-acme-http-solver-bsphl` Running, service `cm-acme-http-solver-4v96s` exists, but `oc get route | grep acme` returns empty

### Fix options discussed
1. **Immediate fix:** Manually create a Route matching the challenge path with `insecureEdgeTerminationPolicy: Allow` (HTTP-01 needs plain HTTP). Route YAML was composed for the user to apply.
2. **Permanent fix option A:** Switch from HTTP-01 to DNS-01 solver (requires DNS API credentials for centos.org zone)
3. **Permanent fix option B:** Upgrade cert-manager-openshift-routes plugin to a version that handles OpenShift Routes natively instead of Ingress objects
4. **Permanent fix option C:** If CloudFront is in the path, configure it to forward `/.well-known/acme-challenge/*` to the OpenShift origin

DNS investigation showed `autosd.sig.centos.org` CNAMEs to `autosd.sig.unmanaged-by.centos.org` - not CloudFront directly.

### Jira history
Three related tickets found in VROOM project:
- **[VROOM-39824](https://redhat.atlassian.net/browse/VROOM-39824)** (Closed Apr 30, 2026) - "Investigate openshift-routes cert manager failure." Most relevant. Hubert investigated the March 2026 incident and identified the exact same root cause on Apr 7: `pathType` must be `Prefix`, and generated routes were missing `shard: external` label. He also found the custom openshift-routes pod was crashing and rebased it. Closed as "couldn't replicate" on Apr 30 - but the fix was never permanently applied, so it recurred.
- **[VROOM-22192](https://redhat.atlassian.net/browse/VROOM-22192)** (Closed Mar 2025) - "SSL cert generation issue for MP+ migration." Origin story: they deployed a custom fork of openshift-routes ([github.com/hubeadmin/openshift-routes](https://github.com/hubeadmin/openshift-routes)) because cert-manager doesn't natively support OpenShift and MP+ restricts cluster-wide permissions. Were waiting on MP+ maintainers to extend namespace-admin role for `certificaterequests/status` and `routes/finalizers`.
- **[VROOM-29984](https://redhat.atlassian.net/browse/VROOM-29984)** (Closed May 2025) - Compliance attestation for cert management controls. Not directly relevant to the fix.

### Resolution
- **Eitan Raviv** is looking into the fix. No further action needed from the user.
- Root cause summary and fix options were shared with the user for communication to the team.

### Open threads
- Permanent fix still needed - without one, this will recur in ~90 days. VROOM-39824 documented the same root cause in April but was closed without a durable fix.
- When Hubert returns from PTO, the custom openshift-routes fork needs to be patched to emit `pathType: Prefix` with the `shard: external` label, or the team should switch to DNS-01 validation.

### Lessons
- OpenShift's ingress-to-route controller silently drops Ingress resources with `pathType: Exact`. cert-manager's ACME HTTP-01 solver uses `pathType: Exact`. This is a known incompatibility that causes cert renewals to fail silently - the solver pod runs fine, but traffic never reaches it because no Route exists. The diagnostic signal is the `IncompleteIngressToRouteRules` event, which is easy to miss among unrelated events (cronjobs, etc.).
- On MP+ (Managed Platform Plus) OpenShift clusters, namespace access for cert troubleshooting requires `oc login` via the console's "Copy login command" flow. The web console can also show Certificate/CertificateRequest resources via Home > Search.
- Previous fix cycles (Ozan in Mar 2026) hit access issues - the solver-side resources looked correct at a glance, masking the missing Route as the real blocker.
- **Closed-as-unreproducible is a smell for intermittent infra failures.** VROOM-39824 identified the root cause but was closed because it "couldn't be replicated" after a manual fix. The underlying Ingress pathType incompatibility remained, guaranteeing recurrence. For infrastructure issues that depend on timing (cert renewal cycles), "can't reproduce now" doesn't mean "fixed" - the fix must be verified against the mechanism, not against current state.

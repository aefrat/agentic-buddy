## PLM/ComposeDB product listing investigation (late session)

Deep-dived into Kanitha's June 11 message in **#rhivos-sp-qc-layered-product** about stale product listings in RHIVOS 2.0-Core errata.

### The problem
Errata [164278](https://errata.engineering.redhat.com/advisory/164278/builds) has stale product listings (22 days old) that include `cross-gcc-c++-ppc64le` and `cross-binutils-s390x/ppc64le` debuginfo RPMs that shouldn't ship to customers. Errata [159850](https://errata.engineering.redhat.com/advisory/159850/builds) has correct listings (updated ~3 days prior). Re-running `compose-composedb-import` and reloading in Errata didn't fix it.

### Resolution thread (RHELWF-14266)
- **Kanitha** opened [RHELWF-14266](https://redhat.atlassian.net/browse/RHELWF-14266), assigned to **Lukas Holecek** (18 comments)
- Root cause: `importtree.py` only **adds** listings, never removes stale entries. Additionally, PLM auto-generates debuginfo listings from parent packages — so even if compose drops debuginfo, PLM infers it exists
- Related known issue: [RHELWF-11979](https://redhat.atlassian.net/browse/RHELWF-11979) — spike filed Oct 2024, references 8+ prior RHEL occurrences. Systemic fix never landed.
- **Fix applied:** Lukas created PLM/ComposeDB overrides via prodlistings API to exclude the specific packages. Workaround, not a systemic fix
- **Open question from Kanitha:** can she delete a listing entirely and re-run fresh? This would prevent recurrence on future RC composes

### Brew verification — hypothesis correction
Initial hypothesis: cross-compiler packages are new in RHEL 10, triggering PLM auto-listing for the first time in RHIVOS 2.0. **Disproven by Brew data:**
- RHEL 9 `binutils-2.35.2-69.el9` produces the same `cross-binutils-{aarch64,ppc64le,s390x}-debuginfo` sub-packages as RHEL 10
- PLM listing for `RHIVOS-1.0.0` (`9Base-RHIVOS-1.0.0`) already contains all three cross-binutils debuginfo entries — **same ghost entries, never noticed**
- Neither RHIVOS 1.x nor 2.0 compose trees contain cross-compiler packages — they're not in any compose's `Packages/` directory
- PLM auto-generates debuginfo listings from the parent `binutils` build in Brew, regardless of what's actually in the compose tree

**Corrected conclusion:** This is not a RHEL version change or a new package. RHIVOS 1.x has had the same phantom PLM entries all along. Kanitha is the first person to check errata advisory builds closely enough to notice — likely because RHIVOS 2.0's errata distribution process is more rigorous than 1.x's was.

## AIIL demo concept — Michael Kuehl (late session)

Investigated Michael Kuehl's June 12 post in #team-pitcrew-automotive: a fully specified RHAS demo proposal titled **"AIIL: AI in the Loop — Issue-to-Release with Closed-Loop HIL Verification"** targeting **ELIV (October 2026)** and **CES27 (January 2027)**.

### Concept
AI agent picks up a GitHub issue in vsomeip → implements fix in sandbox (inner loop/SIL) → Konflux builds RPM + RHIVOS image → Jumpstarter tests on virtual → physical hardware (outer loop/HIL). On failure, agent queries evidence store, hypothesizes, re-enters inner loop. Iteration budget of 3-4, then human escalation.

Evidence collection unified via **correlation contract**: image digest joins evidence plane (Quay, Tekton Results), run_id + lease_id join telemetry plane (Prometheus, Loki). Agent accesses via read-only MCP gateway.

Stack: OpenShift, Konflux, RHAS, Dev Spaces, GitHub, Jumpstarter, Quay, Tekton Chains, Conforma, **ambient-code** (agentic harness), TI SK69 Jacinto (physical target).

## Confluence wiki deep dive — tagging ownership search (continuation session 2)

Read all 25+ pages under two Confluence trees:
- **Auto Toolchain** (196281018) — 22 children: Service Status, Team, RHIVOS Release (13 children incl. Release Documentation, Checklist Template, 6 release checklists, configs matrix), Services/Pipelines/Tools, Package Gating (Design, Gator, RHEL & RHIVOS gating process), Distribution Focus Area (12 children incl. Errata Process, Errata and CDN), Subdomains, etc.
- **Release Management** (196276699) — 3 children: core-rpm checklist, Release Testing Checklist, Smoke Testing Checklist.

### Key finding

The **"RHEL & RHIVOS gating process"** page (387157013) is the closest thing to documenting tagging ownership. It describes two phases:

1. **Development phase:** RHEL builds flow into `-gate` automatically via Brew tag inheritance from `rhel-*-pending`. RHIVOS-native builds land in `-gate` when maintainers build against that tag's build target. No manual tagging needed.
2. **Blocker/Exception phase (RC):** RHEL inheritance is frozen. RHEL builds must be *"added manually"* — **but no owner is named.** RHIVOS builds: maintainers build against `-gate` as before.

The **Release Checklist Template** (196276995) assigns Brew tag creation (task 260: "Create the new tag rhivos-x.y.z in Brew") to `#wg-team-auto-toolchain-release` — but this is about creating the tag structure for a new release version, not about tagging individual packages into `-gate`.

### Confirmed gaps

No Confluence page under either tree documents:
- Who tags RHEL blocker-phase builds manually into `-gate`
- Who has `brew tag-build` permissions for RHIVOS tags
- Side-tag companion rebuild workflow
- dist-git policy exceptions
- z-stream tags (`rhivos-2.0-z-gate`) — not mentioned on any page
- STAG proposal (only in rhivos-workflows-wiki, not Confluence)

**Conclusion:** The gap identified in the earlier 3-repo audit is confirmed by the authoritative Confluence source. The "RHEL & RHIVOS gating process" page acknowledges the manual tagging scenario but assigns no owner. This is the page that should be updated.

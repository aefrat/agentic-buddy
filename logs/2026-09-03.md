# Log — 2026-09-03

## Decisions

- **Jira is the single source of truth for release target dates (release-blocker agent).** Target dates were previously hand-maintained per-release in `release-config.yaml`; the Core/FuSa split duplicated one date onto both tracks and the values had gone stale. Decided to pull each track's target date live from the Jira **fixVersion `releaseDate`** (`query_jira.resolve_target_date`, reading VROOM project versions via `_get('/project/VROOM/versions')`, lru_cached). Reasoning: a single authoritative source removes drift and stale duplication. Config `target_date` fields are now vestigial (only the standalone render-doc CLI still reads them).
- **No silent config fallback for missing target dates — state it explicitly.** User: "Jira is the most trusted source of truth, if there is no Jira data lets clearly state it in the docs." When a fixVersion has no `releaseDate`, the doc renders **"Not set in Jira"** (`render_doc._target_display`) rather than falling back to a config value. This surfaces the data gap instead of hiding it behind a plausible-but-stale number.
- **Publish reviewable copies before touching live docs.** For the "show me the new G-docs for review" request, temporary `[REVIEW]` copies were published for approval; live docs and the Whitney ping were only done after explicit "continue". Reasoning: outward-facing/irreversible actions get a confirmation gate.
- **Dropped the bespoke "submission" release status — two-status model only (Released, Active).** User questioned where the `submission` status meaning came from. Traced it: I coined it during the Core/FuSa split, extrapolated from one descriptive sentence of Whitney's review ("rhivos-2.0 has not been released. This is the FuSa submission release.") — not from any RHIVOS release-lifecycle taxonomy, and applied to exactly one track (2.0 FuSa). User chose to drop it: use `active` for 2.0 FuSa; the "not released" distinction is already carried by simply *not* being `released`. Fully sourced and simpler. Removed `submission` from `_STATUS_BANNER`, the executive-brief branch, config, and tests. Shipped: commit `bcb9166`, 4 live docs republished (2.0 FuSa now reads "Active"), follow-up note posted on VROOM-49388. ruff clean, 8/8 tests.
- **Status legend: visible table, not a hover tooltip (Google Docs constraint).** User asked for a "legend tooltip" explaining each status. Google Docs does not render HTML hover tooltips — the `title` attribute is stripped on HTML→Docs conversion, and there is no native per-word hover in Docs. Deliverable is a visible color-coded legend table placed under the Program summary table, driven by the same `_STATUS_BANNER` dict as the status cells so labels/colors can never drift. Shipped to the Program dashboard: 9/9 tests, committed, republished live. (Now only two statuses to explain: Released, Active.)

## Lessons

- When a data field is duplicated across tracks/config and can drift, prefer a single authoritative source (Jira fixVersion `releaseDate`) fetched live over hand-maintained config. When that source is empty, render the gap explicitly ("Not set in Jira") rather than falling back silently — a visible gap prompts a fix; a stale fallback hides one.
- Substring hazard confirmed again: `rhivos-2.0` is a substring of both `rhivos-2.0-core` and `rhivos-2.0.z`. Track partitioning must use exact set membership (JQL `fixVersion IN`), never `startswith`/`in`. Kept the whole split on exact matching.
- **Self-coined terminology is a liability — flag and remove it.** The `submission` status was a term I invented from a source's *descriptive* sentence and then reified into a named category applied to one track. The tell that something was wrong: writing a legend entry for it felt off, because there was no authoritative definition to cite (bumps Rule 23 "source terminology only" and Rule 10 "no unsourced content"). When a status/category has no authoritative source, don't coin one to fill the gap — express the distinction with what's already sourced (here: "not `released`" needs no third status). Good user catch.
- **Per-track state files leak into commits — `.gitignore` gap.** `.gitignore` ignores `kb/active/*.json` (top level only), but the Core/FuSa split introduced per-track subdirs `kb/active/<release>/<track>/latest.json` which are not matched. They update on every run and got swept into the legend commit by `git add -A`. Cleanup item: widen the ignore pattern (has CI implications) rather than fixing silently.

## System observations

- **Concept candidate:** "Source-of-truth over config duplication + explicit gaps" — when a value is both derivable from an authoritative external system and hand-copied into config, drive display from the external system and render an explicit "not set" state when it is absent, instead of a silent config fallback. Generalizes beyond this agent.
- **Concept candidate:** "Self-coined categories are unsourced content" — when a synthesis reifies a source's descriptive phrase into a named category (status/type/label), that category has no authoritative definition and drifts into unsourced content. Tell: you can't write a definition for it without inventing one. Prefer expressing the distinction with already-sourced primitives. Reinforces Rules 10 and 23. (seen: 1)
- **Concept candidate:** "Platform capability check before honoring a UI request" — a "tooltip" request assumes hover support the target medium (Google Docs) doesn't have (HTML `title` stripped on conversion). Confirm the rendering platform supports the requested affordance before designing to it; offer the closest supported equivalent (visible legend). Ties to existing Google-Docs-conversion-limits observations (anchor links stripped, smart chips invisible).

## Context
- Research question from the user: how does Konflux currently build qcow (disk/VM)
  images, starting from https://konflux-ci.dev/docs/.
- Key finding: Konflux has no bespoke disk-imaging engine. It's a two-stage flow:
  (1) buildah pipeline builds a bootc container image; (2) the `build-vm-image`
  Tekton task (konflux-ci/build-definitions, `task/build-vm-image/0.1/`) runs
  upstream **bootc-image-builder** (BIB) to convert the container into a disk image
  (qcow2, raw, iso, vhd, gce). Disk artifact is pushed as an OCI artifact via
  buildah manifest / skopeo.
- Neither the public docs (konflux-ci.dev/docs) nor the internal user docs
  (konflux.pages.redhat.com/docs/users) document the qcow/disk *build* mechanism.
  Internal docs only cover *releasing* disk images via the
  `push-disk-images-to-cdn` release pipeline.
- Reference implementations: osbuild/bootc-foundry, Fedora Copr.
- Also invoked `/loop` with no task — no recurring job was scheduled (asked the
  user for a task + interval).

## Lessons
- Konflux user-facing docs are container-centric; capabilities like disk-image
  builds live in the build-definitions task catalog and in consumer projects, not
  in the docs. When a doc site comes up short, go to the task/pipeline catalog and
  real consumer repos.
